# ColorBox Lab CRM 🎨🚗

Веб-CRM для сети лабораторий подбора автоэмалей. Система охватывает весь цикл заказа — от приёма клиента менеджером до подбора цвета колористом и итоговой отчётности для директора сети, — с ролевым разграничением доступа и фотофиксацией на каждом этапе.

## Возможности

- **Многоролевая система** — единый вход по логину и токену, автоматический редирект в интерфейс директора, менеджера или колориста в зависимости от роли.
- **Управление сетью филиалов** — директор добавляет и удаляет филиалы, привязывает к ним сотрудников из единого кабинета.
- **Учёт заказов**
  - создание заказа с выбором клиента, авто/детали, кода краски, категории и типа услуги (в т.ч. экспресс-подбор);
  - жизненный цикл статусов: *В очереди → В работе → Готово → Ожидает выдачи → Выдано*. «В работе»/«Готово» выставляет
    только колорист (кнопки «Взять в работу» / «Сдать заказ»); менеджер вручную переводит заказ только в «Выдано»,
    и только когда он уже «Ожидает выдачи» и расчёт (цена) в блоке «Финансы и Оплата» сохранён;
  - доколеровка (`Order.rework_count`) закрепляется за тем же колористом, который вёл заказ — в общей очереди её
    видит только он; менеджер может передать заказ другому колористу филиала (`/order/{id}/reassign-colorist`),
    а колорист — отказаться от своего заказа, тогда он возвращается в общую очередь филиала (`/order/{id}/release`);
  - отмена заказа менеджером — "мягкое удаление": заказ не стирается физически, а переводится в статус *Отменен* и уходит в архив; доступно только менеджеру своего филиала и только пока заказ не выдан;
  - фотоконтроль по этапам работы (деталь до/после, весы, фото рецепта — набор зависит от типа услуги) и отдельно при доколеровке;
  - печатные формы заказа и архива для выдачи на руки клиенту.
- **Финансы** — фиксация цены и статуса оплаты по заказу, агрегированная выручка по филиалу и по сети.
- **Учёт рабочего времени** — открытие и закрытие смены с обязательной фотофиксацией (начало/конец), журнал смен и печатный отчёт для директора.
- **Архив заказов** — фильтрация выполненных заказов по клиенту, автомобилю, статусу оплаты; карточка клиента с историей его заказов.
- **Адаптивный интерфейс** — Tailwind CSS, вёрстка одинаково удобна на телефоне колориста в цеху и на десктопе директора.

## Роли пользователей

| Роль | Основной сценарий | Ключевые разделы |
|---|---|---|
| **Директор** | Управляет сетью: филиалы, сотрудники, сводная аналитика, контроль смен | `/director`, `/director/branches`, `/director/users`, `/director/shifts` |
| **Менеджер** | Принимает заказы от клиентов, ведёт архив, выставляет цену и статус оплаты | `/dashboard`, `/new-order`, `/order/{id}`, `/archive` |
| **Колорист** | Работает по очереди заказов на своём филиале, открывает/закрывает смену, отмечает готовность | `/colorist`, `/shift/start`, `/shift/end` |

Роль и филиал определяются записью пользователя в таблице `users`; доступ к разделам защищён зависимостями `require_login` / `require_director` (см. `utils.py`), при отсутствии прав — редирект на страницу входа.

## Архитектура и структура проекта

Приложение построено на FastAPI с разбиением обработчиков по роутерам под роль пользователя:

```
ColorboxLab/
├── main.py              # точка входа, авторизация, базовый dashboard
├── database.py          # подключение к PostgreSQL, сессии SQLAlchemy
├── models.py             # ORM-модели: Branch, User, Client, Order, Shift
├── utils.py              # шаблонизатор, авторизация, работа с фото
├── init_db.py            # создание таблиц и первичной учётной записи директора
├── routers/
│   ├── director.py       # кабинет директора: филиалы, сотрудники, смены, аналитика
│   ├── manager.py        # заказы менеджера: создание, архив, финансы, печать
│   └── colorist.py       # рабочий стол колориста и учёт смен
├── templates/             # Jinja2-шаблоны (общий layout — base.html)
├── static/uploads/        # загруженные фото (заказы, смены)
└── requirements.txt
```

Каждый роутер инкапсулирует свою предметную область и подключается в `main.py` через `app.include_router(...)`; общая логика авторизации, шаблонов и работы с изображениями вынесена в `utils.py`, чтобы избежать дублирования между роутерами.

## Модель данных

Ключевые сущности (`models.py`):

- **Branch** — филиал сети; владеет сотрудниками, клиентами и заказами.
- **User** — сотрудник (роль: Директор / Менеджер / Колорист), вход по паре `username` + `token` (пароль не используется).
- **Client** — клиент филиала, привязан к своим заказам.
- **Order** — заказ: авто, деталь, код краски, категория, тип услуги, целевой/фактический объём (только положительные значения), статус (включая *Отменен* — заказ отменён менеджером и перенесён в архив), признак экспресс-заказа, счётчик переделок, цена и оплата, фото-слоты, менеджер/колорист-исполнитель, дедлайн. Отдельно — `colorist_deleted_name`: имя колориста, сохранённое на случай удаления его учётной записи (`routers/director.py: delete_user`), чтобы отличать «заказ ждёт колориста» от «заказ делал уже удалённый сотрудник».
- **Shift** — смена сотрудника: время начала/конца и фото-подтверждения для каждого из них.

## Быстрый старт

### Требования

- Python 3.11+
- PostgreSQL (локально или удалённо)

### Установка

```bash
git clone <repo-url>
cd ColorboxLab
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

### Настройка базы данных

По умолчанию используется строка подключения `postgresql://postgres:py@localhost:5432/colorbox`. Создайте базу `colorbox` в вашем PostgreSQL или переопределите подключение через переменную окружения `DATABASE_URL` (см. [Конфигурацию](#конфигурация)).

Инициализация схемы и первого администратора:

```bash
python init_db.py
```

Скрипт создаёт все таблицы и, если он ещё не существует, аккаунт директора:

- логин: `boss`
- токен: `admin_token_123`

### Миграции (Alembic)

Схема версионируется через [Alembic](https://alembic.sqlalchemy.org/). Все новые изменения
`models.py` оформляются миграцией:

```bash
alembic revision --autogenerate -m "краткое описание изменения"
alembic upgrade head
```

На **новой, пустой** базе данных `alembic upgrade head` создаёт всю схему с нуля.

На **уже существующей** базе (созданной раньше через `init_db.py`/старую авто-миграцию) схема уже
совпадает с моделями — в этом случае вместо `upgrade` нужно один раз выполнить:

```bash
alembic stamp head
```

Это помечает текущую схему как соответствующую последней миграции, не пытаясь создать заново уже
существующие таблицы. Дальше все новые миграции применяются обычным `alembic upgrade head`.

`sync_schema()` (запускается автоматически при старте приложения, `database.py`) продолжает
работать как safety-net — она аддитивно досоздаёт отсутствующие таблицы/колонки на случай, если
на каком-то окружении Alembic ещё не накатили.

⚠️ Из-за этого на **уже запущенном** (например, через `--reload`) локальном сервере
`sync_schema()` может успеть сама добавить новые колонки ещё до того, как вы руками выполните
`alembic upgrade head` — тогда команда упадёт с `DuplicateColumn`. В этом случае, как и для
изначально существующей базы, нужен `alembic stamp head` вместо `upgrade` (схема уже соответствует
миграции, просто это сделал не Alembic).

Но источником правды для новых изменений схемы
теперь являются миграции Alembic, а не правки `sync_schema`/`models.py` "на глаз".

### Запуск сервера

```bash
uvicorn main:app --reload
```

Приложение будет доступно на `http://127.0.0.1:8000/`. Войдите под учётной записью директора, затем создайте филиалы и сотрудников (менеджеров и колористов) в разделе `/director/users`.

### Сборка Tailwind CSS

`static/css/tailwind.css` собран заранее и закоммичен в репозиторий — само приложение
Node не требует. Пересобирать его нужно только после изменения классов в `templates/`:

```bash
npm install
npm run build:css      # разовая сборка (static/css/tailwind.css)
npm run watch:css      # пересборка при изменении шаблонов, для разработки
```

Конфиг — `tailwind.config.js` (`content: ["./templates/**/*.html"]`), исходник —
`static/css/tailwind-input.css`.

### Деплой на VPS (systemd + nginx)

`uvicorn main:app --reload` выше — только для локальной разработки (`--reload` следит за
файлами и не предназначен для прода). Готовые конфиги — в `deploy/`:

1. Создать системного пользователя и каталог приложения:
   ```bash
   sudo useradd --system --home /opt/colorbox --create-home colorbox
   sudo -u colorbox git clone <repo-url> /opt/colorbox
   cd /opt/colorbox
   sudo -u colorbox python3 -m venv .venv
   sudo -u colorbox .venv/bin/pip install -r requirements.txt
   ```
2. `cp deploy/colorbox.env.example /opt/colorbox/colorbox.env`, вписать реальный
   `DATABASE_URL`, `chmod 600` и владелец — `colorbox`.
3. `alembic upgrade head` (или `alembic stamp head`, если база уже существовала —
   см. [Миграции](#миграции-alembic) выше).
4. `sudo cp deploy/colorbox.service /etc/systemd/system/`, поправить пути под реальные,
   затем `sudo systemctl enable --now colorbox`.
5. Бэкапы БД: `sudo cp deploy/colorbox-backup.{service,timer} /etc/systemd/system/`,
   `sudo systemctl enable --now colorbox-backup.timer`. Дампы — в `/var/backups/colorbox`,
   хранятся 14 дней. Это защищает от случайного `DROP`/неудачной миграции, но **не** от
   потери самого сервера — дампы лежат на той же машине. Пока фото и БД не переехали на
   S3/managed-хранилище, стоит хотя бы вручную периодически копировать `/var/backups/colorbox`
   куда-то ещё.
6. nginx: `sudo cp deploy/nginx.conf /etc/nginx/sites-available/colorbox`, поправить
   `YOUR_DOMAIN` и пути, `ln -s` в `sites-enabled`, `nginx -t && systemctl reload nginx`.
   Затем `certbot --nginx -d YOUR_DOMAIN` — сам допишет HTTPS и автопродление.

### Обновление на сервере

Каждый следующий деплой — это **`git pull` + `systemctl restart colorbox`**, а не только
`git pull`:

```bash
cd /opt/colorbox
sudo -u colorbox git pull
sudo -u colorbox .venv/bin/pip install -r requirements.txt   # если requirements.txt менялся
alembic upgrade head                                          # если появились новые миграции
sudo systemctl restart colorbox
```

Шаблоны (`templates/*.html`) Jinja2 читает с диска заново на каждый запрос — им рестарт не
нужен. А Python-код (`main.py`, `routers/*.py`, `utils.py` и т.д.) gunicorn/uvicorn загружает
один раз при старте и держит в памяти процесса — `git pull` без рестарта его не подхватит.
Если после деплоя рестарт забыть, получится ровно та ситуация, что уже случалась: старый код
в памяти работает с уже обновившимися шаблонами и падает на рассинхроне (например,
`jinja2.exceptions.UndefinedError` — шаблон ждёт переменную, которую старый код ещё не передаёт).

## Тесты

Автотесты (`pytest`) гоняются на отдельной базе данных, чтобы не задевать локальную/боевую.
Создайте её один раз:

```bash
createdb colorbox_test
```

Запуск:

```bash
python -m pytest
```

По умолчанию тесты подключаются к `postgresql://postgres:py@localhost:5432/colorbox_test`;
переопределить можно переменной `TEST_DATABASE_URL`. Схема создаётся автоматически при первом
запуске (`Base.metadata.create_all`), каждый тест выполняется в своей транзакции с откатом после
теста — тестовая база остаётся пустой между запусками.

Покрытие — не полное, а целенаправленное на самые рискованные и недавно менявшиеся места:
- `tests/test_auth.py` — вход, сессионный токен, его истечение и logout.
- `tests/test_branch_scoping.py` — изоляция данных между филиалами (архив, заказы, клиенты,
  финансы, комментарии) и права ролей на чужие/финансовые действия; колористу закрыт доступ
  к архиву, базе клиентов и карточке клиента (не только на экране — сам роут отдаёт редирект).
- `tests/test_shifts.py` — смены колориста (с фото) и менеджера (без фото), блокировка
  создания заказа без активной смены менеджера, единственная кнопка выхода на пульте колориста,
  отказ при загрузке файла, который не является изображением; заказ, вернувшийся из доколеровки,
  виден в очереди только тому колористу, который его вёл — не любому другому на смене.
- `tests/test_orders.py` — обязательность фото при сдаче заказа по типу услуги, доколеровка,
  запрет отрицательного объёма (требуемого и фактического); директор не может сменить статус,
  загрузить фото или отправить заказ на доколеровку в обход read-only карточки; чужой колорист
  не может перехватить закреплённый заказ, менеджер — передать его колористу другого филиала;
  менеджер вручную переводит заказ только в «Выдано», только из «Ожидает выдачи» и только
  с сохранённой ценой; колорист может отказаться только от своего заказа.
- `tests/test_order_cancel.py` — отмена заказа доступна только менеджеру своего филиала, только
  пока заказ не выдан, отменённый заказ уходит в архив и пропадает из активных списков; отмену
  нельзя протащить в обход роли через общий роут смены статуса.
- `tests/test_clients.py` — создание клиента только менеджером в свой филиал, фильтры истории.
- `tests/test_director.py` — доступ к служебному роуту только директору, безопасное удаление
  сотрудника/филиала (без падения по внешним ключам, без каскадного удаления зависимостей,
  с сохранением имени колориста в `colorist_deleted_name`), отказ при недопустимой роли в форме
  добавления сотрудника.
- `tests/test_utils.py` — граничные случаи разбора id из query-параметров (в т.ч. id=0).

## Карта маршрутов

### Общие

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | Страница входа |
| POST | `/login` | Аутентификация по логину/токену, редирект по роли |
| GET | `/logout` | Выход, сброс cookie |
| GET | `/dashboard` | Рабочий стол менеджера (для директора/колориста — редирект в их разделы) |

### Менеджер (`routers/manager.py`)

| Метод | Путь | Описание |
|---|---|---|
| POST | `/manager/shift/start` | Начало смены менеджера (без фото) |
| POST | `/manager/shift/end` | Конец смены менеджера (без фото) |
| GET/POST | `/new-order` | Создание заказа |
| GET | `/order/{order_id}` | Карточка заказа (свой шаблон под роль: менеджер — редактируемая, директор — read-only, колорист — рабочая) |
| POST | `/order/{order_id}/status` | Смена статуса. «В работе»/«Готово» — только колорист (и только своего заказа, если он уже за кем-то закреплён); «Выдано» — только менеджер, только из «Ожидает выдачи» и с сохранённой ценой |
| POST | `/order/{order_id}/rework` | Отправка выданного заказа на доколеровку (только менеджер) — заказ закрепляется за тем же колористом |
| POST | `/order/{order_id}/reassign-colorist` | Передать заказ другому колористу того же филиала (только менеджер) |
| POST | `/order/{order_id}/release` | Отказаться от заказа (только колорист, только от своего) — заказ возвращается в общую очередь филиала |
| POST | `/order/{order_id}/cancel` | Отмена заказа менеджером → статус *Отменен*, в архив (только менеджер, только пока не выдан) |
| POST | `/order/{order_id}/upload` | Загрузка фото по заказу (менеджер/колорист) |
| POST | `/order/{order_id}/finance` | Цена и статус оплаты (только менеджер/директор) |
| POST | `/order/{order_id}/comment` | Комментарий менеджера/колориста (каждая роль — в своё поле) |
| GET | `/order/{order_id}/print` | Печатная форма заказа |
| GET | `/archive` | Архив выполненных и отменённых заказов с фильтрами (менеджер/директор — колористу недоступен) |
| GET | `/archive/print` | Печать архива (менеджер/директор) |
| GET | `/clients` | База клиентов филиала с поиском (менеджер/директор) |
| GET/POST | `/new-client` | Добавление клиента (только менеджер) |
| GET | `/client/{client_id}` | Карточка клиента и история заказов (менеджер/директор) |

### Колорист (`routers/colorist.py`)

## Работа с фото

Все загружаемые изображения (фото детали, краски на весах, результата, фото открытия/закрытия смены) проходят через `utils.compress_and_save_image`: приведение к RGB, уменьшение до ширины 1280px и сохранение в JPEG с качеством 85 — это снижает нагрузку на хранилище и ускоряет загрузку страниц на мобильных устройствах в цеху. Фото смены могут храниться как список (несколько снимков за одну отметку) и разбираются функцией `utils.parse_photo_list`.
